## 审计结论摘要

当前实际运行的不是完整 Docker 生产架构，而是“宿主机运行 API、Worker、前端，Docker 只运行 MySQL 和 Redis”的本地开发架构。

当前实际运行组件：

- Docker：MySQL、Redis
- 宿主机：FastAPI API、判题 Worker、环境构建 Worker、Vite 前端

当前数据库是 Docker 中的 MySQL 8.4，数据保存在 Docker named Volume 中。当前业务数据明显来自演示数据初始化，数据库中没有 Developer 角色数据。

- docker compose down -v
- docker volume rm
- 删除 Docker 数据根目录
- Docker 数据目录损坏
- 手动删除 /var/lib/docker/volumes/...
- 没有备份就重建 Volume

当前脚本 scripts/dev-down.sh 只停止容器，不删除 Volume。

## 十一、发现的冗余和风险

### 1. 测试 SQLite 残留曾过大

~~~
backend/.pytest-temp-root
约 3.2GB
约 4829 个 test.db
~~~

以上是清理前的规模，已在本轮删除。它们不是业务数据库，测试再次运行时仍可能按 Fixture 自动重新生成；如果重新出现，应在测试完成后再次清理或配置独立的临时目录。

### 2. Docker 历史资源较多

清理前曾存在、目前仍保留的对象包括：

- K12 项目容器
- 历史容器遗留的无主匿名 Volume
- 未能确认归属的其他镜像
- 多个无主匿名 Volume
- Build Cache

其中 K12 资源属于其他项目，不能直接清理；本轮已删除确认无用的 DAI 旧容器、随机失败容器和历史镜像标签。

### 3. 当前 Docker 数据库端口暴露在所有网卡

MySQL 和 Redis 都绑定 0.0.0.0，而不是只绑定 127.0.0.1。如果 Linux 主机防火墙没有限制，局域网内其他机器可能访问 3306 和 6379。

### 4. 开发 Compose 中存在硬编码凭据

docker-compose.yml 中存在开发数据库凭据配置。即使是开发环境，也建议后续改为 .env 或 Docker Secret，避免提交到仓库或被误用于其他环境。

### 5. Redis 开发环境没有 AOF

当前 Redis aof_enabled = 0。Refresh Token 状态和队列状态可能在异常断电后丢失。

### 6. Studio 和媒体文件持久化不统一

开发环境的 backend/storage 是项目目录下的宿主机文件，不是 named Volume。生产 Compose 声明的 studio_data、video_data、cover_data 当前实际不存在。

### 7. 环境构建任务存在异常

数据分析环境和 PyTorch 环境处于 queued，多条构建任务失败，一条 succeeded 任务仍残留 BUILD_FAILED 字段。这可能导致教师看到环境存在但实际无法使用。

### 8. exam_grades 为空

考试答案已经存在，但最终考试成绩表为空。如果这是演示数据设计，应补充文档；如果系统预期自动生成最终成绩，则需要后续排查。

### 9. 备份恢复目前只是待办，不是已落地能力

docs/backup-restore.md 明确说明：

- 真实备份主机待确认
- 备份介质待确认
- RPO/RTO 待确认
- 恢复演练待执行
- 当前不能宣称已经完成生产备份

### 10. Docker Socket 风险

生产 Compose 的 API 和 Worker 使用 Docker Socket。API/Worker 能够操作宿主机 Docker，用户代码执行链路依赖 Docker 权限隔离，需要配合安全隔离、权限控制和风险接受记录。

## 十三、最直观的最终结论

### 1. 现在启动项目到底启动什么？

执行 scripts/dev-up.sh 时：

1. Docker 启动 MySQL
2. Docker 启动 Redis
3. 宿主机执行 Alembic migration
4. 检查或构建判题镜像
5. 宿主机启动 FastAPI
6. 宿主机启动 Judge Worker
7. 宿主机启动 Environment Builder Worker
8. 宿主机启动 Vite 前端

不会启动：

- Nginx
- 完整生产 Compose
- Jupyter
- Celery
- 独立 AI 容器

### 2. 数据库到底在哪里？

当前数据库在：

~~~
Docker 容器 dai-mysql
MySQL 8.4
数据库 dai_platform
~~~

数据保存在：

~~~
Docker Volume:
dai-experiment-platform_dai_mysql_data
~~~

### 3. 删除 Docker 容器后数据会不会丢？

只删除容器，当前 MySQL 数据通常不会丢，因为数据在 named Volume。

但删除 MySQL Volume、Docker 数据根目录、执行 docker compose down -v 或手动删除 Volume 数据目录，都会导致数据丢失。

### 4. Docker Volume 中现在分别有什么？

当前 DAI 项目真正使用的只有：

- MySQL Volume：业务数据库
- Redis Volume：Redis 数据，但当前没有启用 AOF

Studio、Notebook、视频、封面和 Judge 工作文件当前主要在 backend/storage 和 judge-work，不是当前 Docker named Volume。

此外还有 K12 项目 Volume 和历史匿名 Volume。

### 5. 当前数据是怎么产生的？

主要来源：

- seed-demo
- seed-demo --reset-demo
- 基础运行环境 seed
- create-admin
- 业务 API
- E2E seed 脚本
- 测试 Fixture
- Alembic migration

当前业务表数据主要是演示数据，提交记录也带有 seed_fixture 标识。

### 6. Windows 时代的数据现在还在使用吗？

目前没有证据表明 Windows 时期的数据正在被当前 Linux 应用使用。

当前使用的是 Linux Docker 的 dai-experiment-platform_dai_mysql_data。Windows 数据只有在被手动导入或复制到当前 Linux Volume 或目录后，才可能继续影响当前环境。

### 7. 哪些东西确定可以作为清理候选？

清理前的以下候选已经完成处理：

- 已退出且无挂载的随机失败容器
- 旧的 dai-dev-redis
- 旧的 dai-mysql-drift
- 历史 E2E/smoke 镜像

以下对象仍是后续核验候选，但本轮保留：

- dai-dev-redis 和 dai-mysql-drift 原先对应的匿名 Volume
- 无法确认归属的匿名 Volume
- 未列入已核验清单的历史或无标签镜像
- 历史 Build Cache

本轮已完成明确无用资源清理。

### 8. 哪些东西绝对不要随便删除？

绝对不要直接删除：

- 当前 MySQL Volume
- 当前 Redis Volume
- backend/storage
- judge-work
- 当前判题镜像
- 当前基础环境镜像
- K12 项目资源
- 未确认归属的 Docker Volume
- Docker 数据根目录

最终判断：

> 当前项目的真实数据核心是 MySQL named Volume；当前代码和运行文件则大量依赖宿主机目录。Linux 环境目前可以正常运行，测试 SQLite 残留已经清理，但仍存在 Docker 历史资源、Redis 持久化较弱、生产 Compose 未实际运行、环境构建失败以及备份尚未落地等问题。
