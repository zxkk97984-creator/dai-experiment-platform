## 8.1 Storage 持久化

### 当前开发环境

开发环境使用 `LocalFilesystemStorage`。宿主机 API/Worker 通过配置使用项目目录下的：

```text
backend/storage/
```

当前目录约 92 KB，包含历史 Notebook 文件；本轮没有删除或迁移这些文件。开发 Compose 只声明 MySQL/Redis/Jupyter Volume，没有把 `backend/storage` 声明为 Docker Volume。因此：

- 容器删除不会影响宿主机 `backend/storage`；
- 工作区删除、磁盘故障或目录误删会影响文件；
- 该目录必须纳入宿主机文件备份或快照；
- `storage_objects` 目前为空，不能把数据库元数据表误认为已有文件备份系统。

### 生产推荐

生产首选 `S3CompatibleStorage`，通过 `DAI_STORAGE_BACKEND=s3` 和 provider-neutral 的 endpoint、bucket、region、access key、secret key 配置注入。数据库只保存抽象 backend 值 `s3` 和逻辑 object key，不写死 MinIO、AWS 或其他厂商名称。

生产对象存储至少应启用：

- bucket 版本控制；
- 服务端加密或 KMS 加密；
- 最小权限的应用写入/读取身份；
- 访问日志和异常告警；
- 按业务要求设置保留期和不可变备份策略。

### Local production fallback

`docker-compose.prod.yml` 仍保留 Local fallback：

- `studio_data` → `/app/storage/studio`；
- `video_data` → `/app/storage/videos`；
- `cover_data` → `/app/storage/covers`。

该 fallback 只有在以下条件满足时才可用于生产：

1. 三个 named Volume 映射到明确的宿主机/存储盘；
2. Volume 被纳入加密的定期备份；
3. 备份具备校验和和恢复演练证据；
4. 容器重建只重建容器、不使用 `down -v` 或删除 Volume；
5. 磁盘容量、inode、读写失败和备份失败都有监控。

本轮没有切换生产 backend、创建 S3 bucket 或迁移文件。

## 8.3 Secrets 检查与生产注入策略

### 只读检查结果

- Git 跟踪的环境文件只有 `.env.example` 和 `backend/.env.example`，实际 `backend/.env` 未被 Git 跟踪；`.gitignore` 已忽略 `.env`、`.env.local`。
- 未在当前跟踪文件中发现常见的私钥、AWS access key 或真实 API key 格式。
- `docker-compose.yml` 包含开发用途的固定 `MYSQL_ROOT_PASSWORD`/`MYSQL_PASSWORD`；这不是生产可接受的凭据来源。
- `docker-compose.prod.yml` 仍为 DB 用户、DB 密码和 root 密码提供了 `:-` 默认值；如果部署方忘记注入，会形成明显风险。应用生产校验会拒绝部分默认数据库 URL，但不能替代部署层的 fail-closed 配置。
- 生产 Compose 对 `DAI_SECRET_KEY`、CORS、环境基础镜像 digest 和判题宿主目录使用了必填校验；S3 和 AI 凭据通过环境变量注入。
- 当前开发 `backend/.env` 是 development 配置，AI 开关为启用状态且 AI key 已配置；该凭据不应复用到生产，也不应出现在日志、截图、Issue 或提交中。本报告不输出其值。

### 推荐方案

生产部署应使用 Docker Secrets、Vault、云 Secret Manager 或等价的 KMS-backed secret 注入：

- DB root password、应用 DB password、JWT secret、AI key、S3 secret 分别管理；
- 开发、集成、预生产、生产使用不同凭据；
- 生产 secret 不写入 Compose 文件、`.env.example`、镜像层或 Git；
- secret 轮换后同步刷新 API/Worker，JWT secret 轮换需要明确现有 token 的失效窗口；
- 恢复备份时恢复“secret 引用/版本”而不是把明文 secret 放进备份仓库；
- 生产 Compose 的默认凭据建议在下一轮改为 `${VAR:?must be set}`，但本轮按授权只记录风险，没有直接替换配置。

如历史上任何真实 secret 曾被提交或外泄，应先吊销并重新签发；删除文本本身不能视为已修复。

## 8.4 Redis 持久化和事实源策略

### 当前开发状态

当前 `dai-redis`：

- Redis 7.4.10；
- `aof_enabled=no`；
- 默认 RDB save 规则仍存在；
- named Volume 为 `dai-experiment-platform_dai_redis_data`；
- 最终只读复核约 265 个 key，loading=0，最近 RDB 状态为 ok。

本轮没有开启 AOF、没有执行 `SAVE`/`BGSAVE`，没有导出或修改当前 Redis 数据。

### 业务事实源划分

Redis 不是业务唯一事实源：

- 判题提交、考试答案、状态和结果在 MySQL；Redis list 主要负责唤醒 Worker；
- Judge Worker 启动和周期恢复会扫描 MySQL 中的 stale/pending/queued 状态；
- Environment Builder Worker 启动时会对账数据库 build job，并为 queued job 补发 Redis 唤醒；
- 限流计数、运行指标、短期租约和队列消息属于可重建/短期状态；
- Refresh Token 的消费记录和 access-token blacklist 在 Redis 中，因此 Redis 丢失会改变认证行为。

### 推荐策略

生产建议采用：

- AOF `appendfsync everysec` 作为 Redis 状态的主要快速恢复机制；
- 保留周期性 RDB 快照作为灾难恢复和快速装载辅助；
- AOF/RDB 均放在持久化卷，并纳入加密备份；
- Worker 启动恢复逻辑继续以 MySQL 状态为准，不能以 Redis 队列是否存在来判断任务是否完成；
- Redis 备份失败不能阻断 MySQL 业务备份，但必须告警。

生产 Compose 已声明 AOF everysec 和 `redis_data`，本轮没有修改它，也没有在当前开发 Redis 上开启持久化。

### Redis 丢失后的产品行为

- Refresh Token Redis 记录丢失后，刷新请求返回失效，用户需要重新登录；
- Access Token 在其 JWT 有效期内仍可验证；已经写入 Redis 的 blacklist 丢失时，撤销效果最多受 Access Token 剩余有效期影响，当前默认约 30 分钟；
- MySQL 中的账号、课程、提交、考试等业务数据不因 Redis 丢失而消失；
- Worker 会从 MySQL 恢复可重试任务，但已丢失的队列消息可能造成短暂延迟，恢复扫描负责重新唤醒。

## 8.5 备份、恢复和演练策略

### MySQL 备份策略

生产建议：

1. 每日加密全量逻辑备份：`mysqldump --single-transaction --routines --events --triggers --hex-blob --no-tablespaces`；
2. 根据 RPO 需要启用 binlog 归档，支持 point-in-time recovery；
3. 备份写入独立于数据库宿主机的对象存储/备份仓库；
4. 每个备份记录大小、SHA-256、数据库 revision、生成时间和保留截止时间；
5. 定期在隔离数据库中恢复，至少校验核心表计数、Alembic head 和抽样业务关系。

本轮实际从当前开发 MySQL 生成了一份只读逻辑备份，未对源库执行 reset、seed、migration 或业务写入。

### Storage 备份策略

- S3：启用版本控制、跨区域/独立账户备份或等价的第二副本，并对关键对象使用不可变保留策略；
- Local fallback：对 `studio_data`、`video_data`、`cover_data` 做一致性快照或停写窗口归档，记录对象清单和校验和；
- `backend/storage/notebooks` 等历史目录在迁移完成前继续纳入文件级备份；
- 业务数据库和 Storage 备份必须有相同的时间点标记，恢复后分别校验“metadata 有/文件有”和“文件有/metadata 有”；
- 本轮没有创建 StorageObject、没有 backfill、没有移动文件。

### 配置和 Secrets 恢复

- Compose、Dockerfile、Alembic、Storage backend 配置和恢复脚本模板保存在版本控制中；
- 生产 secret 只恢复到 Secret Manager/部署环境，不写入 Git 或普通备份归档；
- 恢复顺序建议为：Secret/配置 → MySQL → Storage → Redis（可选）→ migration 校验 → API/Worker → readiness → 业务抽样。
